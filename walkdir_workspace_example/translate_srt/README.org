#+title: translate_srt
#+language: zh-CN

* 简介

=translate_srt= 是一个批量处理中英双语字幕的命令行工具。它会递归扫描指定目录中的 =.srt= 文件，使用本地 GGUF 大模型直接在进程内完成翻译，并把中文译文写到对应英文行之后。

程序会直接修改源 SRT 文件。首次处理重要字幕前，建议先备份文件或将文件纳入版本控制。

* 功能

- 使用 Clap 解析目录和运行参数。
- 使用 WalkDir 递归查找 =.srt= 文件，扩展名不区分大小写。
- 保留字幕序号、时间轴、空行及原有换行风格。
- 忽略 HTML 和 ASS 格式标签，仅识别可见英文文本。
- 同一字幕时间轴块中已有中文时跳过该块，避免重复翻译。
- 使用内嵌的 llama.cpp 推理后端直接加载 =.gguf= 模型，不再依赖 HTTP 翻译服务。
- 使用 Tokio 多线程运行时并发读取和处理文件；单个大文件的翻译批次也会并发执行。
- 整个进程共享一个 GGUF 模型实例和一个 llama.cpp 上下文，由独立线程持有；多个翻译请求作为互相独立的序列在同一次前向计算中批量解码（见「性能」）。
- 首尾完整的独立句会按批（默认最多 20 行）封装成带编号的 HTML 段落；跨时间轴的续句片段使用单行请求，防止翻译服务把相邻字幕内容合并或重复写入。若批量响应缺失段落或不同原文得到相同译文，会保留可信译文并只重试可疑行；完全无法还原时才二分子批次。
- 空译文、纯标点等不含中文的结果不会写入文件，而是按缺失译文重试。
- 请求失败时最多尝试 3 次，并使用 250ms、500ms 的退避等待。
- 单个文件只有在全部待翻译行成功后才会写回。

* 运行要求

- Rust 工具链，建议 Rust 1.95 或更高版本。
- 一个可直接加载的 =.gguf= 模型文件，例如 =gemma-3-4b-it-q4_0.gguf=。
- 若希望在 macOS 上使用 GPU 加速，构建时需要启用 =metal= feature。

* 构建

#+begin_src shell
cargo build --release -p translate_srt
#+end_src

在 macOS 上启用 Metal：

#+begin_src shell
cargo build --release -p translate_srt --features metal
#+end_src

* 使用

当前命令行形式：

#+begin_example
translate_srt [OPTIONS] --model-file <FILE> [DIRECTORY]
#+end_example

处理指定目录：

#+begin_src shell
cargo run --release -p translate_srt --features metal -- \
  --model-file ~/backup-20251212/gemma-3-4b-it-q4_0.gguf \
  /path/to/subtitles
#+end_src

不提供目录时，程序使用当前工作目录：

#+begin_src shell
cargo run --release -p translate_srt --features metal -- \
  --model-file ~/backup-20251212/gemma-3-4b-it-q4_0.gguf
#+end_src

已经构建二进制时也可以直接运行：

#+begin_src shell
translate_srt --model-file ~/backup-20251212/gemma-3-4b-it-q4_0.gguf /path/to/subtitles
#+end_src

** 命令行参数

| 参数 | 默认值 | 说明 |
|------+--------+------|
| =[DIRECTORY]= | 当前工作目录 | 递归扫描的字幕目录 |
| =-j, --jobs <JOBS>= | =max(2, 可用 CPU 数 / 2)= | 同时处理的最大文件数 |
| =--model-file <FILE>= | 无 | 本地 GGUF 模型文件路径 |
| =--cpu= | =false= | 强制使用 CPU 推理 |
| =-v, --verbose= | =false= | 输出更详细的 llama.cpp 日志 |
| =--request-delay-ms <MILLISECONDS>= | =0= | 每个翻译请求完成后的额外等待时间 |
| =--batch-size <LINES>= | =20= | 单次翻译请求合并的最大字幕行数 |
| =--slots <SLOTS>= | 按推理设备自动选择 | 模型同时并行解码的翻译请求数 |
| =-h, --help= | - | 显示帮助 |
| =-V, --version= | - | 显示版本 |

=--slots= 的默认值：Metal（显存与内存共用）取 32；CUDA/Vulkan 按显存取 32/16/8/4；纯 CPU 取 8。

例如，模型推理负载较高时，可以增加请求间隔：

#+begin_src shell
translate_srt --model-file ~/backup-20251212/gemma-3-4b-it-q4_0.gguf \
  /path/to/subtitles \
  --request-delay-ms 250
#+end_src

指定模型文件并限制到 CPU：

#+begin_src shell
translate_srt /path/to/subtitles \
  --model-file ~/backup-20251212/gemma-3-4b-it-q4_0.gguf \
  --jobs 4 \
  --cpu
#+end_src

* 性能

单条请求逐 token 解码时，GPU 每生成一个 token 都要把整个模型权重读一遍，速度受显存带宽限制而不是算力限制。因此程序把并发翻译请求作为互相独立的序列放进同一次前向计算：一次权重读取同时推进所有在途请求。

在此基础上还做了两件事：

- *共享提示词前缀缓存*：每条请求的提示词开头（系统指令那一段）完全相同。程序在启动时把这段前缀解码进一个专用序列，之后每条请求通过 llama.cpp 的序列复制引用同一批 KV 单元，只需要预填充真正不同的那几十个 token。
- *KV 缓存按需分配*：缓存是一个共享池，请求在准入时按实际需要计费，而不是每路都预留最大上下文。因此提高 =--slots= 主要增加吞吐，而不会成倍占用显存。

在 M4 Max 上用 =gemma-3-4b-it-q4_0.gguf= 翻译 18 个字幕文件（共 1168 行）的实测：

| 版本 | 耗时 | 峰值内存 |
|------+------+----------|
| 串行解码（旧） | 247s | - |
| 批量解码 =--slots 32=（新） | 63s | 5.9 GiB |

解码采用贪心采样（与旧版温度为 0 的采样链等价），因此结果稳定；但批量矩阵乘法的浮点累加顺序与单条解码不同，个别行的译文可能有细微差异（实测 1168 行中有 8 行用词不同，语义一致）。

程序结束时会在 stderr 打印一行推理统计（步数、平均并发路数、前缀缓存命中的 token 数），可用于调整 =--slots=。

* 限制

- SRT 文件必须使用 UTF-8 编码。
- 中文检测以字幕块中的常用 CJK 字符为依据。如果一个字幕块同时包含尚未翻译的英文和已有中文，程序会保守地跳过整个字幕块。
- 当前版本不再通过 HTTP 调用外部翻译服务；所有翻译都依赖本地 GGUF 模型质量与机器算力。
- 单条请求的提示词加译文不能超过 3072 tokens；超出时该请求会报错，调用方会把批次拆小后重试。
