* SQLx + Alloy U256 + PostgreSQL NUMERIC 示例

这个用例把完整的 =alloy_primitives::U256= 存入 PostgreSQL =NUMERIC=，并直接在
SQL 中进行数值比较、排序和累加。

** 数据库类型

=financial_data.amount= 使用不限定精度的 =NUMERIC=：

#+begin_src sql
CREATE TABLE IF NOT EXISTS financial_data (
  id SERIAL PRIMARY KEY,
  amount NUMERIC NOT NULL
);
#+end_src

实际 migration 还增加了 U256 约束：

- =scale(amount) = 0=，拒绝小数；
- =amount >= 0=，拒绝负数；
- =amount <= U256::MAX=，拒绝超出 256 位无符号整数范围的值；
- =amount= 上的 B-tree 索引支持等值、范围和排序查询。

没有使用 =NUMERIC(78, 0)=，因为 PostgreSQL 会先把带小数的输入舍入到 scale 0；
使用不限定精度的 =NUMERIC= 配合 =CHECK= 可以直接拒绝小数输入。

** SQL 数值运算

数据库现在把 =amount= 当作真正的数值，可以直接执行：

#+begin_src sql
-- 比较和排序
SELECT id, amount
FROM financial_data
WHERE amount > 100
ORDER BY amount;

-- 累加
SELECT SUM(amount)
FROM financial_data;

-- 原子加法
UPDATE financial_data
SET amount = amount + 100
WHERE id = 1;
#+end_src

** Rust 与 SQLx 的类型边界

=alloy-primitives= 的 SQLx 实现把 =U256= 映射为 =BYTEA=，不能直接绑定到
=NUMERIC=。本例在边界处把 =U256= 转成十进制文本，并在 SQL 内显式转换：

#+begin_src sql
INSERT INTO financial_data (amount)
VALUES ($1::TEXT::NUMERIC);
#+end_src

读取时使用 =amount::TEXT=，再由 =U256::from_str_radix(..., 10)= 恢复成
Rust 的 =U256=。转换是十进制整数文本，不经过 =f32=/=f64=，因此不会损失精度。

SQL 的 =SUM(amount)= 可能超过单个 U256 的最大值，所以示例把总和作为十进制文本
返回，而不强制转换回 =U256=。

** 运行

#+begin_src shell
docker run \
  --name my_postgres \
  -e POSTGRES_PASSWORD=PgSuper2026! \
  -d \
  -p 5432:5432 \
  postgres:18.3

export DATABASE_URL='postgres://postgres:PgSuper2026!@localhost:5432/sqlx_alloy_u256_example'
sqlx database create
cargo run -p sqlx_alloy_u256_example
#+end_src

程序每次运行都会追加五条示例数据，然后由 PostgreSQL 执行阈值比较和
=SUM(amount)=。如果需要重新得到空表，请重建示例数据库。

这次已经重写 migration 历史。如果旧数据库执行过原来的 =u256_values= migration，
需要先重建数据库：

#+begin_src shell
sqlx database drop
sqlx database create
#+end_src
